# 外部系统独立文案生成接口对接说明

本文档供外部系统开发人员使用，说明如何在没有 AI 系统工单、广告系列 ID、选题 ID 或文案草稿 ID 的情况下，直接提交广告文案生成任务并查询生成结果。

## 1. 接口说明

该接口是独立的异步文案生成接口：

- 外部系统不需要先创建工单。
- 不需要提供内部 `campaign_id`、`work_order_id`、`topic_id` 或 `draft_id`。
- 提交成功后返回 `job_id`。
- 外部系统使用 `job_id` 轮询查询生成结果。
- 一次请求可以生成 1 至 5 组文案。
- 该接口不会把生成内容写入内部工单、选题或文案草稿业务流程。

接口基础地址：

```text
https://ai.ggcss.xyz
```

创建文案生成任务：

```http
POST /api/v1/integrations/ai/copy
```

查询任务状态和结果：

```http
GET /api/v1/integrations/ai/jobs/{job_id}
```

## 2. 鉴权方式

推荐通过请求头传递访问令牌：

```http
Authorization: Bearer <AI_ADS_ACCESS_TOKEN>
Content-Type: application/json
```

也支持通过 URL 查询参数传递：

```text
?ai_access_token=<AI_ADS_ACCESS_TOKEN>
```

安全要求：

- 不要把访问令牌写入前端公开代码、公开仓库、日志或截图。
- 服务端之间调用时，优先使用 `Authorization: Bearer ...`。
- 查询任务结果时也必须携带访问令牌。

## 3. 调用流程

1. 外部系统生成一个唯一的 `external_request_id`。
2. 调用文案生成接口提交业务信息。
3. 接口返回 HTTP `202`、`job_id` 和建议轮询间隔。
4. 按照 `retry_after_seconds` 等待后，使用 `job_id` 查询任务。
5. `status = processing` 时继续轮询。
6. `status = succeeded` 时读取 `copywritings`。
7. `status = failed` 时停止轮询并记录 `error`。

## 4. 请求字段

### 4.1 接口必填字段

| 字段 | 类型 | 必填 | 限制 | 说明 |
| --- | --- | --- | --- | --- |
| `product_name` | string | 是 | 1-255 字符 | 产品、应用、游戏、服务或广告对象名称。 |

从接口校验角度看，只有 `product_name` 是必填字段。例如：

```json
{
  "product_name": "Explore India TV"
}
```

该最小请求可以生成文案，但因为业务信息较少，生成内容可能比较通用。正式对接建议同时提供下方的推荐字段。

### 4.2 推荐业务字段

| 字段 | 类型 | 必填 | 限制或默认值 | 说明 |
| --- | --- | --- | --- | --- |
| `external_request_id` | string | 强烈建议 | 最大 128 字符 | 外部系统本次生成请求的唯一 ID，用于幂等和问题排查。 |
| `brief` | string | 建议 | 无固定格式 | 文案生成要求，例如平台、文案方向、核心目的和语气。 |
| `selling_points` | string[] | 建议 | 默认 `[]` | 产品卖点列表。建议每一项只表达一个卖点。 |
| `language` | string | 建议 | 最大 32 字符 | 期望生成语言，例如 `en`、`en-US`、`zh-CN`。 |
| `audience` | string | 建议 | 无固定格式 | 目标受众描述，例如年龄、兴趣和使用场景。 |
| `country` | string | 建议 | 最大 128 字符 | 投放国家或地区，例如 `IN`、`US`。 |
| `landing_url` | string | 建议 | URL 字符串 | 广告落地页地址，为模型提供产品和转化上下文。 |
| `event_name` | string | 可选 | 最大 128 字符 | 优化事件名称，例如 `purchase`、`registration`。 |
| `customEventType` | string | 可选 | 最大 128 字符 | 明确的外部事件类型，例如 `PURCHASE`。优先级高于自动识别。 |
| `count` | integer | 可选 | `1-5`，默认 `1` | 本次生成的文案数量。 |
| `constraints` | object | 可选 | 默认 `{}` | 语气、CTA、长度或禁用表达等生成约束。 |

建议至少提供：

```text
external_request_id
product_name
brief
selling_points
language
audience
country
count
```

### 4.3 可选广告上下文字段

外部系统已有广告系列、广告组或创意信息时，可以直接传递以下 JSON 对象。这里传的是外部业务信息，不是 AI 系统内部 ID。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `campaign` | object | 否 | 外部广告系列信息。 |
| `adset` | object | 否 | 外部广告组、国家、受众或优化事件信息。 |
| `creative` | object | 否 | 外部创意、落地页或 CTA 信息。 |

常用字段示例：

```json
{
  "campaign": {
    "name": "Explore India TV - July",
    "objective": "OUTCOME_SALES"
  },
  "adset": {
    "countries": "IN",
    "audience_description": "Men aged 25-45",
    "customEventType": "PURCHASE"
  },
  "creative": {
    "link": "https://example.com/landing",
    "btn_type": "SHOP_NOW"
  }
}
```

### 4.4 `constraints` 示例

`constraints` 是可扩展 JSON 对象，可用于表达本次文案的额外要求。例如：

```json
{
  "tone": "clear and trustworthy",
  "cta": "SHOP_NOW",
  "platform": "Facebook",
  "length": "short",
  "prohibited_terms": [
    "guaranteed",
    "risk-free"
  ]
}
```

注意：`constraints` 中的字段属于生成提示信息，不是全部具有固定枚举或强制校验。外部系统应使用稳定、清晰的键名和文本值。

### 4.5 顶层字段限制

请求采用严格字段校验。未在本文档中定义的额外顶层字段会导致请求失败。

不要直接增加类似字段：

```json
{
  "topic_id": "...",
  "work_order_id": "...",
  "unknown_field": "..."
}
```

额外业务要求应放入 `constraints`、`campaign`、`adset` 或 `creative` 对象中。

## 5. 完整请求示例

```bash
curl --request POST \
  --url "https://ai.ggcss.xyz/api/v1/integrations/ai/copy" \
  --header "Authorization: Bearer <AI_ADS_ACCESS_TOKEN>" \
  --header "Content-Type: application/json" \
  --data '{
    "external_request_id": "copy-20260714-001",
    "product_name": "Explore India TV",
    "landing_url": "https://example.com/landing",
    "audience": "Men aged 25-45 who want easy home entertainment",
    "country": "IN",
    "event_name": "purchase",
    "customEventType": "PURCHASE",
    "language": "en",
    "brief": "Generate direct Facebook ad copy emphasizing simple setup and everyday entertainment.",
    "selling_points": [
      "Premium channels",
      "Simple setup"
    ],
    "constraints": {
      "tone": "clear and trustworthy",
      "cta": "SHOP_NOW",
      "length": "short"
    },
    "count": 2
  }'
```

## 6. 创建任务返回

创建成功时，接口返回 HTTP `202 Accepted`：

```json
{
  "code": 1001,
  "message": "processing",
  "data": {
    "asy_task_id": "01JEXAMPLECOPYTASK001",
    "job_id": "01JEXAMPLECOPYTASK001",
    "status": "processing",
    "retry_after_seconds": 2
  }
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `code` | integer | `1001` 表示任务处理中。 |
| `message` | string | 当前为 `processing`。 |
| `data.job_id` | string | 后续查询任务状态和结果使用的任务 ID。 |
| `data.asy_task_id` | string | 兼容字段，当前与 `job_id` 相同。外部系统建议统一使用 `job_id`。 |
| `data.status` | string | 当前任务状态，创建时为 `processing`。 |
| `data.retry_after_seconds` | integer | 建议等待多少秒后再查询。 |

## 8. 结果字段说明

### 8.1 任务结果字段

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `data.job_id` | string | 文案生成任务 ID。 |
| `data.status` | string | 成功时为 `succeeded`。 |
| `data.request_id` | string | 优先返回外部传入的 `external_request_id`；未传时返回任务 ID。 |
| `data.copywritings` | object[] | 生成的文案列表，数量通常与请求的 `count` 一致。 |

### 8.2 单组文案字段

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `primary_text` | string | 广告主文案，可作为 Facebook/Meta Primary Text。 |
| `headline` | string/null | 广告标题。模型未返回时可能为 `null`。 |
| `description` | string/null | 广告补充描述。模型未返回时可能为 `null`。 |
| `cta` | string | 模型生成或请求指定的 CTA 原始值。 |
| `call_to_action` | string | 标准化后的 CTA，例如 `LEARN_MORE`、`SHOP_NOW`、`SIGN_UP`。 |
| `customEventType` | string/null | 外部传入或根据 `event_name` 识别的事件类型。无法识别时可能为 `null`。 |
| `copywriting` | object | 兼容用的嵌套文案对象，与上层主要文案字段重复。 |

外部系统推荐直接读取：

```text
data.copywritings[*].primary_text
data.copywritings[*].headline
data.copywritings[*].description
data.copywritings[*].call_to_action
data.copywritings[*].customEventType
```

## 9. 任务失败返回

生成任务失败时：

```json
{
  "code": 5001,
  "message": "ai generation failed",
  "data": {
    "asy_task_id": "01JEXAMPLECOPYTASK001",
    "job_id": "01JEXAMPLECOPYTASK001",
    "status": "failed",
    "error": "provider error message"
  }
}
```

外部系统必须同时检查：

- HTTP 状态码。
- 响应中的 `code`。
- `data.status`。

查询接口可能通过正常 HTTP 响应返回业务失败结果，因此不能只根据 HTTP `200` 判断生成成功。

## 10. 错误处理

| 场景 | HTTP 状态 | `code` | 处理建议 |
| --- | --- | --- | --- |
| 访问令牌缺失或错误 | `401` | 不固定 | 检查 `Authorization` 请求头。 |
| 请求字段缺失、类型错误或包含未知顶层字段 | `400` | `4001` | 根据 `data.errors` 修正请求。 |
| `job_id` 不存在或不是外部 AI 任务 | `404` | `4001` | 检查保存的 `job_id`。 |
| 任务仍在执行 | `200` | `1001` | 按 `retry_after_seconds` 继续轮询。 |
| 任务执行成功 | `200` | `0` | 读取 `data.copywritings`。 |
| AI 服务或任务执行失败 | 通常为 `200` 或 `500` | `5001` | 记录 `job_id` 和 `error`，根据策略重试。 |

## 11. 幂等和重试要求

`external_request_id` 用于识别同一次外部业务请求。

推荐格式：

```text
copy-<外部业务ID>-<时间或版本>
```

例如：

```text
copy-ad-987654-v1
```

处理规则：

- 因网络超时不确定任务是否创建成功时，使用相同的 `external_request_id` 重新提交。
- 相同 `external_request_id` 会复用原任务，并返回原来的 `job_id`。
- 不要使用相同 `external_request_id` 提交不同请求内容，否则仍会得到原任务结果。
- 修改生成要求、重新生成一批文案，或原任务失败后需要重新执行时，应使用新的 `external_request_id`。

## 12. 外部系统实现要求

外部系统应完成以下逻辑：

1. 安全保存访问令牌。
2. 为每一次独立生成请求创建唯一 `external_request_id`。
3. 保存创建接口返回的 `job_id`。
4. 按 `retry_after_seconds` 轮询，不要高频请求。
5. 以 `data.status` 判断任务是否结束。
6. 成功后保存完整的 `copywritings` 数组，而不是只保存第一组。
7. 失败时记录 `external_request_id`、`job_id`、`code` 和 `error`，便于双方排查。
8. 客户端自行设置合理的总轮询超时时间；超时不代表服务端任务一定失败，可稍后继续使用原 `job_id` 查询。

## 13. 对接验收清单

- [ ] 不需要 AI 系统内部工单或业务 ID 即可提交。
- [ ] 创建请求返回 HTTP `202` 和 `job_id`。
- [ ] 相同 `external_request_id` 重复提交返回相同 `job_id`。
- [ ] 查询接口能正确处理 `processing`、`succeeded`、`failed` 三种状态。
- [ ] `count > 1` 时能够保存多组文案。
- [ ] 外部系统能够读取 `primary_text`、`headline`、`description` 和 `call_to_action`。
- [ ] 访问令牌不会出现在前端公开代码或日志中。
- [ ] 任务失败或查询超时时能够保留 `job_id` 供后续排查。
