# 外部视频轮询 / 下载优化方案

## 背景 / 现状（已核对代码）

外部视频和外部图片的架构**本质不同**，图片那套「同步死等 100 多秒 + 120s httpx 超时 + 不重试」的问题不会在视频上原样复现：

- 图片：`GatewayImageProvider.generate_images` 同步 POST 网关，死等 107~141s 出图。
- 视频：火山引擎 Seedance 是「提交任务 + 轮询」异步模式，真正渲染在火山侧排队：
  - POST `create_video` → `start_generation` 只提交任务、立刻拿到 `provider_job_id` 返回（不等渲染）。
  - GET `/jobs/{job_id}` → `get_generation_status` 查状态（快请求）。

因此视频**不会因为渲染时间长而超时失败**。但排查发现视频有它自己的三个隐患：

### 隐患 1（主要）：轮询时在 Web 进程里同步下载整个视频

当火山引擎报告 `succeeded`，触发状态翻转的那次 GET 会**在请求里同步下载整段视频再落地**：

- 代码：`backend/app/services/video_service.py` 的 `refresh_video_generation` → `video_storage.transfer_provider_video(...)`。
- 触发点：`backend/app/services/external_video_generation_service.py` `get_job`，当 `status == GENERATING and provider_job_id` 时调用 `refresh_video_generation`。
- 下载上限：`video_download_timeout_seconds = 120.0`、`video_download_max_bytes = 500MB`（`config.py` 第 103~104 行）。

问题：该下载发生在**单进程 backend 的 GET 请求**里（不是 celery worker），会占住这条请求和一个 DB 连接最多 120 秒，正是对方感受到的「视频接口很慢 / 顶不住」。更糟的是：若对方 HTTP 客户端超时较短，在我们下完前就断开 → 下次轮询又从头全量重下（写 `.tmp` 再 replace），可能反复空跑。

> 说明：500MB 上限对 12 秒 Seedance 视频足够，不会因「超大小限制」失败；且下载只在状态翻转那一次触发（之后 `status=GENERATED` 不再 refresh），不是每次轮询都下。

### 隐患 2（次要）：视频 provider 超时写死、工厂未传

`VolcengineVideoProvider.__init__` 默认 `timeout_seconds=60.0`，但 `backend/app/integrations/video/factory.py` 创建时**根本没传这个参数**，无法通过 env 调整。60s 对提交/查状态够用，但与图片修复不一致。

### 隐患 3（次要）：提交(POST)无自动重试

`create_video` 里一旦 `start_generation` 撞火山瞬时 5xx，整个 POST 直接失败，需对方重新提交。图片走 `generation_task` 有 `max_attempts`，视频这条链没有。

## 目标

1. 把「succeeded 后的视频转存下载」移出 GET 轮询路径，避免单进程 Web 被大文件下载阻塞、避免对方超时断连导致反复重下。
2. 视频 provider 超时做成可配置（与图片修复对称）。
3. 视频提交(`start_generation`)瞬时失败时有限次重试。
4. 不修改 `.env` / `.env.production`（只在示例文件记录新配置）。

## 改动清单

### 任务 A（主要）：视频转存移出 GET 轮询路径

**目标语义**：GET 轮询只做「查状态 + 记录 provider 临时 URL」，**不在请求里下载大文件**；真正的本地转存交给后台执行；本地文件就绪前，`url` 可暂时返回 provider 的临时 URL 或维持 `processing`。

**推荐实现方向（Codex 需先确认现有基建再落地）**：

1. 拆分 `refresh_video_generation`，把「同步 `transfer_provider_video`」与「状态同步」解耦：
   - 状态同步部分（`get_generation_status` + 写 `status`/`provider_video_url`/`error_message`）保留在 GET 路径，保持快。
   - 当检测到 `succeeded` 且尚未本地转存时，**不在 GET 内下载**，而是调度一个后台转存任务，并把 `metadata_json.implementation_status` 标为 `pending_transfer`。
2. 后台转存复用现有 Celery 视频队列（`docker-compose.prod.yml` 里的 `worker_video` / `video_queue`）。确认现有 `generation_task_dispatcher` / worker 任务是否可承载「视频转存」这类任务；若没有现成任务类型，新增一个专门的转存任务（幂等：已转存则跳过）。
3. GET 返回逻辑：
   - `succeeded` 且本地已转存 → 返回本地 `url`（现状）。
   - `succeeded` 但本地未转存完 → 可选择返回 provider 临时 URL，或仍返回 `processing`（需与对接方确认哪种更合适；见「对接方约定」）。
4. 保证幂等与并发安全：同一 `video_id` 不重复转存；转存中途失败可被后台重试，而不是靠对方轮询触发全量重下。

> 决策点（Codex 落地前需确认）：
> - 现有 Celery 是否已有可直接复用的视频后台任务入口；`GenerationTaskService` 是否适合承载「纯转存」任务，还是新建独立任务。
> - 本地未转存完时 GET 对外返回 `processing` 还是 provider 临时 URL——影响对接方拿到的 `url` 是否是我方域名。

**涉及文件（预估）**：
- `backend/app/services/video_service.py`（拆分 refresh，去掉 GET 内同步下载）
- `backend/app/services/external_video_generation_service.py`（`get_job` 语义调整）
- 后台任务相关：`backend/app/services/generation_task_dispatcher.py` / `backend/app/worker/tasks.py`（按最终方案）
- 对应测试：`tests/test_external_video_generation.py`

### 任务 B（次要）：视频 provider 超时可配置

1. `backend/app/core/config.py` 新增：
   ```python
   volcengine_video_timeout_seconds: float = Field(default=60.0, ge=1, le=600)
   ```
2. `backend/app/integrations/video/factory.py` 的 `VolcengineVideoProvider(...)` 调用新增：
   ```python
           timeout_seconds=settings.volcengine_video_timeout_seconds,
   ```
3. `.env.example` / `.env.production.example` 记录：
   ```env
   VOLCENGINE_VIDEO_TIMEOUT_SECONDS=60
   ```

### 任务 C（次要）：视频提交有限次重试

- 在 `ExternalVideoGenerationService.create_video` 调用 `start_video_generation` / `start_generation` 处，对 `ProviderError`（网关瞬时 5xx / 网络错误）做有限次重试（如 2~3 次、带小退避）。
- 注意区分**可重试错误**（网络、5xx）与**不可重试错误**（入参校验、时长超范围等 `AppError`），后者不重试直接抛。
- 重试不得造成重复创建火山任务失控：确认失败发生在拿到 `provider_job_id` 之前才重试。

## 给外部对接方的约定

- `/api/v1/integrations/video-generation/jobs/{job_id}` 是**异步长任务**，渲染在火山侧排队，建议轮询 **3~5 秒/次**、带退避。
- 若采用「本地未转存完返回 provider 临时 URL」的方案，需提醒对方：临时 URL 可能过期，最终应以我方域名的本地 URL 为准。
- 失败时读取响应 `data.error` 字段定位原因。

## 提交前检查

- `git status --short` 不得出现 `AGENTS.md`、`.env`、`.env.production`。
- 只改：`config.py`、`video/factory.py`、`video_service.py`、`external_video_generation_service.py`、后台任务相关文件、对应测试、两个 `.env*.example`。
