# 外部多图备用模型补偿设计

## 目标

在不修改外部系统请求格式、任务 ID 或轮询方式的前提下，外部图片生成任务应保留已经成功的图片；仅为失败图片切换备用模型继续生成。

## 范围与约束

- 仅修改 AI 系统 `advertising-automation` 后端。
- 外部系统继续使用现有的 `POST /integrations/image-generation/images` 请求，`count` 仍可为 1 到 5。
- 不修改外部系统 `pixel_project` 的代码，也不要求外部系统拆分请求。
- 任务最终全部模型均耗尽时保持 `failed` 状态，但查询结果必须返回已成功图片。
- 已成功图片不得在后续自动重试或人工重试中重复生成或覆盖。

## 当前问题

外部多图任务会以一个父任务并发提交多个图片请求。当前优先备用路由只允许 `count=1` 的任务在 `provider_timeout`、`provider_429` 或未知供应商错误后切换模型。因此 `count>1` 时，即使其中部分图片已经成功，整个父任务仍在同一个故障供应商上耗尽全部重试次数。

## 设计

### 槽位状态

父任务的 `result` 保存固定数量的图片槽位。每个槽位至少具有：

- `index`：与外部请求顺序一致的 1 起始编号。
- `status`：`queued`、`running`、`succeeded` 或 `failed`。
- `image`：成功时的已转存图片结果，包括 URL、storage key、prompt、size、模型和元数据。
- `error`：失败时的错误码和错误信息。

父任务已存在的成功槽位是权威结果。任何后续执行仅构造未成功槽位的图片 brief。

### 路由与重试

首次执行按既有 `priority_fallback` 路由选择主供应商。若至少一个未完成槽位遇到可重试的供应商错误：

1. 已成功槽位立即保存在父任务结果中。
2. 父任务保留现有自动重试次数和延迟。
3. 路由整体前进到下一个备用供应商：`jbb_gpt_image`、`dm_fox_gpt_image` 或 `alita_gpt_image` 到 `cpa_gemini`，再到 `volcengine`。
4. 下一次执行只生成未成功槽位。

父任务内不混用同一轮次的模型；跨轮次允许不同槽位来自不同模型，并在每张图片的元数据中保留真实模型和供应商。

### 终态与接口

- 全部槽位成功：任务为 `succeeded`，返回全部图片。
- 自动重试耗尽：任务为 `failed`，保留 `result.images` 中已经成功的图片，返回 `generated_count` 和每个失败槽位的错误信息。
- 所有槽位失败：保持当前失败语义，图片列表为空。

现有外部请求不变。查询响应中的 `images` 在失败但存在成功槽位时从空数组变为部分图片，是兼容性的新增数据；调用方仍可依据既有 `status=failed` 判断整体未完成。

### 幂等与持久化

每轮生成结束后先转存并持久化成功槽位，再触发父任务失败和自动重试。重试从结果中筛选非 `succeeded` 槽位，防止重新调用模型或重复转存成功图片。已有 `external_request_id` 幂等逻辑保持不变。

## 测试标准

- 三图请求中两张首选模型成功、一张超时：重试仅调用备用模型生成第三张，最终成功并返回三张图片。
- 三图请求中两张成功、最后一张耗尽备用模型：父任务为 `failed`，查询结果仍返回两张成功图片。
- 多图任务在 `provider_timeout` 后确实前进到备用路由，并记录路由历史。
- 重试不重新调用已成功槽位，也不产生重复图片或 storage key。
- 全部失败的任务继续返回空图片列表。
